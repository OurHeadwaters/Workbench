## 2. What CCM ops is and is not

**What it is.** An operations management tool for a small-team regional
abattoir. It tracks the full processing pipeline for individual animals:
booking → received → slaughtered → aging → cutting → ready for pickup →
picked up. Supporting features: cut sheets (farmer-specified cutting
instructions), status event log, farmer notifications, packaged yield
tracking, yield-estimate accuracy reporting, and a read-only farmer
self-serve portal (auth via 6-digit one-time code).

**What it is explicitly not.**
- Not a Codetry implementation or proof-of-concept.
- Not a marketplace, platform, or multi-tenant SaaS.
- Not a wholesale logistics or distribution tool (fragments of that
  problem are noted in docs as a future concern; nothing is built).
- Not an idea-incubation layer. No Fodder, Fallow, or Nursery concepts
  of any kind.

## 4. The governing constraint at this zone

The load-bearing constraint for CCM ops is **single-animal, single-owner
traceability.** Every record in the system traces to one animal, one
farmer, one cut sheet. The data model does not support carcass splitting
across buyers, shared ownership, or aggregate lot tracking. This is a
deliberate scope bound — it keeps the v0.1 tractable and honest.

Operationally: the CCM tool begins when a booking is created and ends
when the farmer picks up the processed boxes. Everything before (the
farm) and everything after (resale, distribution, wholesale) is
deliberately out of scope for this artifact.

## 5. Vocabulary discipline at this zone

Words that have clean, single-referent definitions here:

- **Animal** — one individual animal moving through the pipeline.
- **Booking** — a scheduled processing date for one or more animals
  from one farmer.
- **Cut sheet** — the farmer's per-species cutting and packaging
  instructions.
- **Status event** — an immutable log entry recording a pipeline
  transition.
- **Notification** — a message record generated by a status transition,
  awaiting delivery.
- **Packaged yield** — the actual take-home weight and cut breakdown
  logged by the operator post-cutting.
- **Yield estimate** — the algorithmic fallback (species yield factor ×
  hanging weight × primal share model) when no actual is recorded.
- **Portal** — the farmer-facing read-only view, auth-gated by one-time
  code.
- **Operator** — CCM staff (internal).
- **Farmer** — the animal owner / CCM customer (external).

No Codetry vocabulary (Nursery, Fodder, Fallow, Saltbox, Eave,
Both-States, Shallows) has been introduced into this project's code,
schema, or UI. The constellation zone-naming in documentation
(`replit.md`) references the personal constellation (Zone 4 = Regen
Revolution) not the Codetry model.

## 9. Locked decisions

1. **Single-animal traceability is the scope boundary.** Carcass
   splitting, lot aggregation, and wholesale batch tracking are
   explicitly out of scope for v0.1. Not to be reopened without a
   clear next-zone designation.
2. **PII discipline.** No real names of farmers, operators, or
   individuals appear in code, schema seed data, or documentation.
   Substitution map: Karen → "the operator," Black Barn → "Pilot Farm,"
   Lisa Koshel → "the backup producer," Sam Caldwell → "Pat Rivers."
   This was a deliberate, completed scrub (May 8, 2026). Do not
   reintroduce real names.
3. **Portal auth is OTP-only, no password.** 6-digit one-time code
   matched against farmer email or phone. Bearer token minted on
   verification, 30-day TTL. No password reset flow, no OAuth.
   Deliberate simplicity for v0.1.
4. **No SMS/email provider for v0.1.** Code is logged to console;
   non-production responses return the code directly. This is the
   documented demo-mode behaviour, not an oversight.
5. **Orval codegen is the API client.** No hand-rolled fetch in the
   frontend except for the SSE-like streaming (none exists yet in CCM;
   applies by convention). Generated hooks are the contract.
