This is effectively the architecture spec for the standalone project.

Tier 2 — Directly Transferable Technical Building Blocks
5. Meeting Companion — the audio pipeline Bright Side needs
This is the most underappreciated RT asset in the project. Meeting Companion is a polished, production-ready audio recording and AI analysis app. It uses MediaRecorder with IndexedDB offline resilience (so a recording survives a network drop — critical on a care floor), uploads to the API server, runs through OpenAI's Whisper model for transcription, then a second GPT pass for speaker diarization and slide deck generation. The PWA setup (service worker, manifest.json, iOS home-screen install, display: standalone) means it runs like a native app on a facility iPad. Every single one of these capabilities is what Bright Side's session recording feature needs. The code is already written, tested, and running. The Bright Side standalone project should be pulling directly from this pattern.

6. API server infrastructure
The shared Express + Drizzle ORM + PostgreSQL backend is the same stack the RT tool was built on. Bearer-token auth, email via Resend, OpenAI integration, structured error handling, Zod validation — all of this is already built and could be referenced or replicated in the standalone. The pattern for a route protected by a password-gated Bearer token (exactly how RT_PASSWORD worked) is demonstrated everywhere in this codebase.

7. Email flows via Resend
The project already has templated transactional emails (order confirmations, gift delivery alerts, app design intake confirmations). The Resend integration is live and tested. Bright Side's family invitation email, "session nudge" alert (if a facility hasn't run a session in 14 days — flagged as a retention risk in the business plan), and weekly bright-moments digest email could all be built directly from these patterns.

Tier 3 — Feature Concepts Worth Carrying Forward
8. Director dashboard — the Parr's Jars Admin as a reference
The admin page at /admin in Parr's Jars has revenue cards, top-sellers analytics, day-of-week charts, repeat-customer counts, and a "rule-based suggestions" engine. The RT director dashboard had a parallel structure (Overview analytics, Residents engagement, Nudges). The Parr's Jars admin is a working reference for how the Bright Side director dashboard should feel — data-forward, scannable, not clinical.

9. Abandoned cart / session nudge logic
The Parr's Jars cart recovery system (tasks #64, #65 in the proposed queue) sends recovery emails to customers who didn't complete checkout. Bright Side's business plan explicitly flags "if a facility has not run a session in 14 days, trigger a proactive check-in" as a retention strategy. The trigger-and-email pattern for that nudge is directly transferable.

10. The "champion" model and warm-referral pipeline
The custom labels B2B page and the wholesale distributor package both use a model of: warm referral → qualified lead → manual checkpoint before any commitment. The business plan recommends the same model for Bright Side: identify one motivated staff "champion" per facility, build on personal contacts first, offer free pilots in exchange for case studies. The Parr's Jars wholesale page (Task #17, merged) is a live reference for how to build that B2B offer page.

Tier 4 — Strategic / Business Intelligence

Across Parr's Jars, AI tools are framed as "Implementation Agent (IA) — real shipped tools, not chatbots and vibes."
