3. Audio autoplay fix + a major dead-code cleanup
This is the most important part of the handoff.

The bug. For weeks the audio refused to autoplay in the deployed iframe even after several rounds of "broaden the unlock listeners" attempts. The previous code attached unlock handlers like this:

['pointerdown','pointermove','pointerover','touchstart','mousedown',
 'mousemove','click','keydown','wheel','scroll','focus','focusin']
  .forEach(evt => document.addEventListener(evt, handler, { once: true }));
document.addEventListener('visibilitychange', handler);
The fatal flaw: once: true plus events that DO NOT count as user activation in Chrome's autoplay policy. pointermove, pointerover, mousemove, focus, focusin, scroll, and visibilitychange all fire WITHOUT a real user gesture — and the visibilitychange event fires the moment an iframe becomes visible, before the user has done anything. Because the listeners were once: true, the very first stray non-gesture event would (a) fire the handler, (b) call ctx.resume() which silently rejected because there was no real activation, (c) detach every listener in the same call. After that, no real click could ever unlock audio. The corner "tap to start" dot was a dead button — its handler had already self-removed seconds before the user noticed.

The fix. The new src/lib/video/ambient-audio.ts does this instead:

Listens only on events that actually qualify as user activation: pointerdown, mousedown, touchstart, touchend, click, keydown, wheel. No pointermove, no mousemove, no pointerover, no focus, no focusin, no scroll, no visibilitychange in the unlock list.
No once: true. The listeners self-detach only after performUnlock() has awaited ctx.resume() AND verified ctx.state === 'running'. If the resume didn't take, listeners stay attached and the next real gesture can still unlock.
performUnlock() is async — it awaits the resume promise before declaring success, so a half-resumed context never burns the unlock attempt.
If you ever need to add a new gesture-trigger entry point, never add events that fire without user activation, and never use once: true without verifying the unlock actually succeeded. Both mistakes are now load-bearing rules to avoid for this code.

The cleanup. ambient-audio.ts went from 933 lines to ~330 — about a 65% reduction. Everything sitting behind the long-disabled ENABLE_PROCEDURAL_MUSIC = false flag was deleted: a kick / snare / hi-hat scheduler, sub-bass and piano-stab and brass-swell synth functions, the BPM/beat-phase/chord-timeline tables, an oscillator chord pad, an LFO modulator, a high-shelf filter, a music bus, a duck-gain envelope, the per-scene chord-morph effect, plus the SceneAudioProfile type and the fadeIn / fadeOut controls that had no callers. The orphaned captions component src/components/video/KineticLyrics.tsx was also deleted — it had no importers after the CC toggle was removed.

What's left in the audio pipeline is the bare minimum:

HTMLAudioElement → MediaElementSource → voiceGain → outputGain (the unlock gate)
                                                  → AnalyserNode → ctx.destination
Public API of useAmbientAudio is unchanged for its three call sites (VideoTemplate, DancerOverlay, AudioVisualizer): it still returns { muted, toggleMute, getAnalyser, getVoiceAudio, tryStart }. The currentScene parameter is accepted but no longer needed internally — kept for backward compatibility with any future scene-driven audio work.
