2. Saltbox — The Full Picture
What it does day-to-day (from the user's experience):
Saltbox is a daily homeschool companion that lives on a phone as a PWA. On a given morning, Bobbie opens it to see the day's shape: what's scheduled, what children are doing, what materials are queued. It holds the library of actual files (PDFs, audio, images) attached to lessons — not links, the files themselves — so nothing breaks when a curriculum site goes down. It tracks units, lesson resources, narration prompts, copywork passages. It has a Responsibilities section with personality-aware coaching for neurodivergent learners. It can generate a Family Recap for grandparents. It supports meal planning and kitchen timers. It has a Portfolio for capturing completed work and a Moments section for significant days.

What problem it solves for this specific user:
Bobbie has inattentive ADHD and is homeschooling a neurodivergent child. The structural problem it solves is: maintaining continuity of structure when working memory and executive function are unreliable. It's a low-friction daily anchor. Opening it in the morning is the triage step, not the planning step — the day is already shaped, she's just reading it. It replaces the mental overhead of holding "what are we doing today, where is that PDF, what did we cover, what does she need next" in working memory.

What it has replaced or made unnecessary:
Based on the codebase: external curriculum management apps, file-link-based approaches (broken links are explicitly called out as the failure mode the library solves), and the overhead of cross-referencing multiple tools. The Learning Hub (methodology cards, slow tour of homeschool styles) is built in — so Bobbie doesn't need to find external resources to understand Charlotte Mason, classical, unschooling, etc.

Is it in daily active use?
Active development is confirmed. Daily use is probable given the user profile (user = developer = proof), but this agent cannot confirm cadence of daily use — honest gap. The codebase shows recent work on onboarding, the Learning Hub tab, restore-from-backup, and iOS Safari layout fixes — all consistent with a tool being lived in, not just built.

3. Neurodivergent Design Decisions
What is captured in the codebase and design system:

Cognitive load reduction:

Mobile-first, 44px minimum tap targets — no precision required
No emojis in UI (explicit rule) — visual noise reduction
No push notifications, no badges on load — pull-only, calm UX
No red for destructive actions — warm amber instead (removes anxiety signal)
Fraunces serif headings + Inter body — distinct hierarchy without density
Task initiation support:

Today page is the primary entry point — day is pre-shaped, not a blank slate
LearningHubTodayTrack on the home page surfaces the next learning card without requiring navigation
Morning triage card connects to Gmail inbox — reduces the "what do I need to check" overhead
Working memory accommodation:

Library holds actual files (not links) — removes the "where did I save that" failure mode
Narration prompts stored per-resource — one tap to see the question, no recall required
Copywork passages stored per-resource — same
Both-States design principle (works empty and full from day one) — no "set everything up before it's useful" friction
Hard days / low-activation accommodation:

The onboarding wizard has a "restore from backup" shortcut on step 0 — minimum friction to recover from device loss
Learning Hub is positioned as "no quiz, no scoring, no club to join" — explicitly removes performance pressure
Saltbox primitive: "one bounded thing you can point at" — scope is always clear, no sprawl
What is explicitly excluded:

No account required for Saltbox (gather) — no login friction
No backend for Saltbox — no "it's down" failure mode
No social features — pull-only, no community pressure
No gamification — no streaks, no badges in the homeschool tool
Gap: The Responsibilities page's "personality-aware coaching" is listed as a feature but the exact neurodivergent-specific design decisions within it are not surfaced in this summary — would require deeper code review.

4. The Governing Metaphor / Design Constraint
The Saltbox primitive is the load-bearing metaphor for this project. From the Codetry doctrine:

Saltbox: one bounded thing you can point at.
This functions as the design spec in the same way the fence functions for Bright Side. Every feature must be a Saltbox — a bounded, nameable thing. The Library is a Saltbox (your files, here). The Responsibilities section is a Saltbox. The Portfolio is a Saltbox. The constraint prevents scope creep by requiring that any new feature pass the test: can you point at it? Can you name it in one phrase? Can it exist on its own?

The Both-States test is the secondary constraint: every feature must work when empty and when full, from day one. No "add three things and then it becomes useful" features.

The Both-Sides test is the vocabulary constraint: every concept must have a vernacular name (for Bobbie) and a massity/grant-language name (for funders). This applies across the constellation, not just Saltbox.

7. Institutional / Funding Dimension
Is Saltbox structured for adaptation?
Not currently. It is wired to Bobbie's household model — her children, her library, her units. There is no multi-tenant model, no profile system, no "configure for a different household" layer. The data model is flat and single-household.

What a "port" would look like:
Generic methodology (transferable):

Local-first PWA architecture (no backend, no account)
Both-States/Saltbox primitive as feature gate
The neurodivergent design decisions (no red, no gamification, no performance pressure, pull-only)
The Learning Hub card format (methodology cards, slow tour)
The Library model (files, not links)
Specific to Bobbie's household (would need replacement):

The specific curriculum areas (Charlotte Mason, classical, etc.)
The ADHD-inattentive + neurodivergent child configuration
The family structure assumptions (single caregiver, one child being schooled)
The XRPL/Zone identity layer (irrelevant to a general disability tool)
Funding mechanisms — what the codebase suggests:
The brief artifact contains an Economic Development One-Pager (NOHFC/FedNor) and a Partnership & Funding Brief — these are the instruments Bobbie is using to position the broader Codetry model for institutional funders. There is no Saltbox-specific funding document visible here.

PHI/personal data gate (equivalent to Bright Side's):
Yes — and it's stronger than Bright Side's. Saltbox stores everything locally (IndexedDB + localStorage). No data ever leaves the device unless liveShare.enabled === true (the live follow-along link, off by default). There is no server-side personal data at all. This makes it procurable without institutional overhead — there is no data custodian, no privacy officer needed, because the data never leaves the household device. This is a structural procurement advantage if adapted for supported individuals.

9. Tech Stack and Artifact Structure
Stack:

Monorepo: pnpm workspaces
Node.js 24, TypeScript 5.9
Frontend: React + Vite (all artifacts)
Backend: Express 5 + Drizzle ORM + PostgreSQL
Validation: Zod (zod/v4), drizzle-zod
API codegen: Orval (from OpenAPI spec in lib/api-spec)
Build: esbuild (CJS bundle for server)
XRPL: zone-identity lib for wallet primitives
AI: Claude Haiku (The Field / Fridge to Table suggestion endpoint only)
Object storage: Replit Object Storage (family-buckets photo uploads)
Email: Resend (Sandbox Sunday digest, requires RESEND_API_KEY)

Database schema highlights:
Tables exist for: sandbox households + posts + invite tokens + events, family-buckets chores + savings + memory entries + helpers, inbox/share/storage routes. Saltbox (gather) has no database — everything local.

AI constraints:
Claude Haiku is used only for the ingredient-to-meal suggestion endpoint. No AI touches Saltbox, North Star, Sandbox, or any Zone 0 personal data. This is structural, not incidental.
